# 改旧稿：把早于当前合同的笔记改到第五章标准

用于用户说「这篇很难读 / 很多东西没展开」，而笔记是旧版本（七位置不全、块后一两句、大块 30–50 行）的情况。**不是从零写新稿**：源码、锚点、事实都已在稿子里，任务是重排与加厚，不是重写整篇。

## 0. 先量，再动手

```text
python scripts/audit_lesson.py notes/阶段/正式课.md --json
```

看四个数：`blocks` 里每块 `per_line`、`density` 告警、`knowledge_gap` 告警、`position` problems。
按块分三档：`<30` 重写、`30–50` 加厚、`≥50` 只修结构。**不要按章平均用力**，先修用户读到的入口单元。

动手前必须留可恢复基线：复制到 `revision-baselines/<version>-before/`，不要只依赖 Git（笔记常在 ignored 目录）。

## 1. 把旧标题映射到七位置

旧稿常见的编号标题，按内容对应到固定位置，逐单元改，不改写内容只改骨架：

| 旧标题（示例） | 七位置 |
|---|---|
| 1. 问题与思路 | 实际问题与实现思路 |
| 2. 真实触发输入 | 架构位置、真实触发与输入准备 |
| 3. 源码位置、符号与阅读准备 | 源码定位与阅读准备 |
| 4. 真实代码 / 源码摘录 | 4–5 连续源码与紧邻逐行推导 |
| 5. 本地正常顺序与失败边界 | 同输入局部运行与实际重要失败 |
| 6. 框架机制和对象所有权 | 机制与工程判断 |
| 7. 上下游与改动影响 | 怎么用、上下游、接入与修改影响 |

改名要和内容加厚同轮做。只改名不加厚，读者看到的还是旧骨架；只加厚不改名，审计的 `position` 永远不会清零。一个单元一轮，改完立刻跑审计。

## 2. 拆大块，不重打代码

旧稿常见 30–50 行一整块，块后正文被摊薄。按真实动作切成 5–15 行，**代码必须从原稿切片，不能手抄或重打**：

- 先把原块的行按语义边界分组（guard / 对象构造 / 状态提交 / 收尾）；
- 用脚本把原 fence 按行切片，生成多个新 fence，保证字节一致；
- 每片后面写 2–4 段，目标 50 字/行（复杂 65）；
- 切完核对：新稿的每个代码片段都能在原稿里逐字节找到，fence 数量变化符合切片数。

## 3. 每个引用后按三问补

旧稿的 bullet 往往只答了第一问（这一行是什么）。逐块补：

1. **怎么读**：语法、求值、绑定、坑；
2. **实际触发什么**：框架/运行时/存储做了什么，带类名、默认值、版本或异常；
3. **不这样会怎样**：换写法的代价、写错的可见后果、从哪排查。

每块再补两条整块的「看不见的事实」（一条框架契约、一条底层或设计）。旧 bullet 里的事实一条不删；要合并时先确认事实已在新句子里。

## 4. 单元收尾补三节

旧稿常常「代码讲完就断」。每个单元末尾补：

- **运行边界**：同一输入的中间值、停止点、失败残留；
- **机制判断**：至少一个替代方案与代价；
- **怎么用**：一个具体改动追接线位置、漏改的可见后果。

## 5. 验收

- 审计 `position` 清零；`density` 里该单元没有 `<50`（允许复杂块 65 目标下的 50–65）；
- fence 数为偶数、每段新代码能在旧稿找到；
- 事实对照：旧稿每条 bullet 至少映射到新稿一句，不出现「只删不并」；
- 只改一个单元就保存一次，下一单元重新跑审计，不要整篇改完再验。

## 不做什么

- 不为过门禁删代码、缩范围或把 bullet 改成一句摘要；
- 不把「改旧稿」当成「重写新稿」：已有的正确事实、锚点、revision 全部沿用；
- 不在同一轮里既改骨架又改全部内容：先骨架，再逐块加厚，读者和审计都能看到中间态。
